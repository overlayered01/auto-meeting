# 캘린더 일정 녹음 · 음성 미감지 자동 종료

작성: 2026-09-16 · 앱 0.2.0+2 · Android 우선

## 구현된 경로와 남은 경로

| 항목 | 이번 구현 |
|---|---|
| 여러 Google 계정의 내 캘린더 | Android에 등록되어 기기에 동기화·표시된 캘린더를 읽고 개별 선택 |
| 개인 일정 | 참석자 이메일 없이 시작·종료 시간이 있는 일정으로 판단 |
| 네이버 직접 로그인·조회 | 미구현. 공개 API는 일정 추가만 제공하며 Android CalDAV는 공식 미지원 |
| 네이버 일정이 기기 Calendar Provider에 실제 동기화된 경우 | 해당 캘린더가 앱 목록에 나타나면 선택 가능. 실제 네이버 동기화 경로는 미확인 |
| 일정 시작 | 사용자가 미리 켠 마이크 Foreground Service가 일정 시각에 수집 시작 |
| 말소리 미감지 자동 종료 | Silero VAD가 60초 연속 음성을 감지하지 못하면 저장·종료 |
| 저장 | 기기 전용 WAV 16kHz / 16-bit / 모노, 약 1.92MB/분. 기존 테스트 M4A 유지 |

Google 계정을 이 앱에 직접 OAuth 로그인하는 방식이 아니다. 계정 추가·인증 갱신·서버 동기화는 Android의 Google 계정 및 캘린더 동기화 앱이 담당한다. 네이버 캘린더 앱에서 Google 일정을 볼 수 있다는 사실은 반대로 네이버 자체 일정이 기기 제공자에 공개된다는 의미가 아니다.

근거: [Android Calendar Provider](https://developer.android.com/identity/providers/calendar-provider), [네이버 공개 API 목록](https://developers.naver.com/docs/common/openapiguide/apilist.md), [네이버 CalDAV 지원 범위](https://help.naver.com/service/5620/bookmark/2426?osType=COMMONOS).

## 사용 순서

1. 새 APK로 업데이트한다. 앱을 삭제하지 않고 업데이트하면 기존 녹음이 유지된다.
2. 하단 `캘린더` 탭에서 마이크·알림, 캘린더 읽기, 알람 및 리마인더 권한을 허용한다.
3. `Google 계정 추가`로 필요한 계정을 Android에 등록한다. 각 계정의 캘린더 동기화 및 표시가 켜져 있어야 한다.
4. `기기 일정 새로고침`을 누르고 녹음할 캘린더만 선택한다. 처음에는 아무 캘린더도 자동 선택하지 않는다.
5. 화면의 조회된 일정 목록을 확인하고 `캘린더 자동 대기 켜기`를 누른다. 확인 창에서 자동 녹음 조건을 확인한다.
6. 대기를 켠 이후에 시작하는 일정에서 녹음한다. 화면 잠금·홈 이동·최근 앱 목록 제거 시에도 이 대기 모드는 유지하도록 구현했다. 알림 또는 앱에서 끌 수 있다.
7. `녹음함`에서 일정명·캘린더·종료 이유와 파일을 확인한다. 재생·내보내기·삭제하려면 자동 대기를 먼저 끈다.

설정에서 강제 중지하거나 재부팅한 후에는 앱을 열어 대기를 다시 켠다. 기존 녹음 테스트 탭의 기본 모드/잠금 실험 모드와 캘린더 모드는 별개다.

## 녹음 정책

- 대기 세션은 최대 12시간이며 만료되면 사용자가 다시 켜야 한다. 한 파일은 최대 4시간이다.
- 대기 시작 전에 이미 시작한 일정은 소급 녹음하지 않는다.
- 종일 일정, 취소 일정, 참석 거절 일정, 종료 시간이 시작 시간보다 늦지 않은 일정은 제외한다.
- 첫 음성이 없더라도 녹음 시작 후 60초간 말소리를 감지하지 못하면 종료한다.
- 말소리가 감지되면 미감지 시간은 0으로 초기화된다. 다음 말소리까지 다시 연속 60초를 센다.
- 침묵 조건, 일정 종료, 수동 종료, 4시간 상한, 대기 세션 종료 중 먼저 도달한 조건으로 마무리한다.
- 한 일정이 침묵으로 끝나도 해당 일정 시간 안에서 다시 녹음하지 않는다. 실행 영수증은 파일 삭제와 별도로 유지된다.
- 동일 UID와 시작 시각을 가진 중복 일정은 하나로 취급한다. 제공자가 UID를 주지 않으면 출처별 ID를 사용하므로 계정 간 중복 판별은 제한된다.
- 서로 다른 일정이 겹치면 먼저 시작한 녹음을 유지하며 새 일정은 `overlapping_event`로 건너뛴다. 제목이 같다는 이유만으로 합치지 않는다.
- 시작을 30초 넘게 놓친 일정은 지연 실행하지 않고 건너뛴다.
- 일정의 이동·삭제·종료 변경이 기기 제공자에 반영되면 예약을 재계산한다. 녹음 중인 일정이 사라지거나 시작 시각이 바뀌면 현재 녹음을 마무리한다.
- 캘린더 선택은 대기를 끈 뒤 변경한다. 계정 삭제 시 목록에서 사라진 출처의 일정은 다음 정상 조회 후 제외된다.

## 음성 감지와 파일

`AudioRecord PCM → WAV 저장 + Silero VAD → 연속 미감지 60초 판정`

마이크를 두 번 열지 않고 같은 PCM 샘플을 사용한다. 음량 임계값만으로 사람 말소리를 판별하지 않는다. 음성/비음성 판정은 기기 안에서 실행하며 녹음 업로드나 음성 인식 서버 호출은 없다. VAD는 말을 글자로 변환하거나 화자를 식별하지 않는다. TV·스피커의 말소리도 음성으로 판단할 수 있고, 작은 목소리·소음에서 오판할 수 있다.

16kHz, 512-sample(32ms) 프레임을 사용한다. 정상적으로 읽고 분류한 PCM만 미감지 시간을 증가시킨다. 마이크 읽기 오류, 5초간 입력 정체, Android의 마이크 차단은 정상적인 침묵으로 취급하지 않는다. 저장 중 남은 공간이 20MB 미만이면 중단한다. WAV 헤더는 종료 시 실제 PCM 길이로 갱신한다. 강제 종료로 남은 파일은 `interrupted`이며 복구 성공이라고 표시하지 않는다.

신규 WAV는 압축 M4A보다 크다(1시간 약 115MB). 일정명과 계정은 앱 내부 기록에 저장하고 UUID 파일명에는 넣지 않는다. 진단 복사에는 일정명·계정 이메일을 넣지 않는다. OS 백업 제외 설정은 유지하며 기기별 실제 백업 동작까지 보장하지 않는다.

사용 라이브러리: [android-vad 2.0.10 / Silero](https://github.com/gkonovalov/android-vad/tree/2.0.10), ONNX Runtime Android 1.22.0. 고정 버전으로 의존성을 선언했다. [제3자 구성요소 안내](THIRD_PARTY.md).

## 예약과 동기화의 한계

앱이 보이는 상태에서 사용자가 마이크 Foreground Service를 시작한다. 이후 AlarmManager는 이미 실행 중인 서비스가 일정을 확인하도록 깨울 뿐, 종료된 마이크 서비스를 몰래 재시작하지 않는다. 대기 내내 CPU WakeLock을 잡지 않고, 조회 때 최대 15초, 실제 녹음 중에만 제한된 WakeLock을 사용한다.

기기 일정은 7일 범위의 반복 일정 인스턴스로 조회한다. ContentObserver와 실행 가능한 동안 약 1분 간격 조회를 함께 사용하며, 예약 시각에도 다시 읽어 변경·삭제를 확인한다. 전체 조회가 실패하면 이전 목록을 삭제하지 않지만 새 녹음은 시작하지 않는다. 녹음 중 조회가 실패하면 보수적으로 해당 녹음을 마무리한다.

UI의 최근 조회 시각은 **기기 제공자를 읽은 시각**이지 Google/네이버 서버의 최신 동기화 확인 시각이 아니다. Doze, 정확한 알람 호출 빈도 제한, 계정 동기화 지연, 제조사 절전으로 실행·변경 반영이 늦을 수 있다. 기존의 짧은 잠금 테스트 성공으로 12시간 대기 성공률을 확정하지 않는다. [Android 알람 제약](https://developer.android.com/develop/background-work/services/alarms), [마이크 서비스 실행 조건](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

## 검증

- 사용자 보고: 갤럭시 S23 / Android 16에서 이전 버전 잠금 실험 정상. 신규 음성 감지·12시간 대기 검증 결과는 아님.
- Flutter 자동 테스트: 16개 통과.
- Android 단위 테스트: 19개 통과(기존 정책 6, 일정·음성 미감지 정책 11, WAV 헤더 2).
- Android 디버그 APK 빌드 성공.
- Android 16(API 36) 에뮬레이터 통합 실행: 아래 결과 확인. 별도 로컬 테스트 캘린더만 사용했고 실제 Google·네이버 계정 데이터는 사용하지 않았다.

| 통합 시나리오 | 실제 결과 |
|---|---|
| 캘린더 권한·정확한 알람 허용, 캘린더 선택, 사용자 확인 후 대기 | 기기 제공자 목록 조회 및 마이크 FGS 시작 확인 |
| 대기 중 추가한 미래 일정, 화면 잠금 유지 | 시작 시각보다 202ms 뒤 녹음 시작 |
| 말소리가 없는 입력 60초 | `saved / speech_absent_60s`, WAV 오디오 길이 60,000ms |
| 별도 20초 일정의 종료 시각 도달 | `saved / event_ended`, WAV 길이 19,904ms |
| 위 녹음과 겹친 다른 일정 | `missed / overlapping_event`, 마이크·파일 생성 없음 |
| 녹음 중 테스트 일정 삭제 | `saved / event_removed_or_ended`, 15,200ms 파일로 마무리 |
| 사용자 대기 종료 후 | 서비스 종료 확인, 녹음함에서 신규 WAV 재생 시작 확인 |

테스트 기록 ID: 침묵 종료 `3ceeadd0-4091-48aa-9bef-ab3603fdfaa9`, 일정 종료 `d42700dc-b80c-49b1-b552-bd2e6360f2e6`, 겹침 `ae2d2047-ccc8-41af-8e9f-050acfa24c16`, 삭제 반영 `cbd4310e-7160-4848-8b6d-394ebacf58eb`.

호스트 오디오 입력·출력을 끈 가상 기기이므로 실제 사람 목소리, 음질, 감지 정확도, 사람이 들은 재생 결과를 검증한 것이 아니다. 동일 일정 재시작 방지·발화 후 타이머 초기화는 단위 테스트로 확인했다. 장시간 Doze와 실제 계정 간 동기화는 미검증이다.

가상 기기 콜드 부팅 직후 첫 앱 실행에서 입력 응답 시간 초과(ANR)가 1회 발생했다. 당시 높은 메모리 압박 및 Flutter 표면 생성 대기 스택을 확인했으며 기다리기 후 UI가 정상 표시되었다. 이후 위 흐름은 수행됐지만 초기 실행 성능과 실기기 재현 여부는 추가 확인 대상이다.

실기기에서 확인할 항목:

1. Google 계정 두 개의 서로 다른 내 캘린더 선택 및 반복·개인 일정 조회
2. 대기 시작 후 2분 뒤 일정, 잠금 상태 자동 시작, 말하다가 60초 멈춘 뒤 저장
3. 중간에 말하면 타이머 초기화, 처음부터 말하지 않아도 60초 뒤 종료
4. 일정 종료가 먼저 오면 즉시 종료, 종료된 일정에서 다시 녹음하지 않음
5. 일정 이동·삭제, 캘린더 선택 변경, 계정 삭제, 겹침과 반복 일정의 다음 회차
6. TV·음악·작은 목소리·통화·마이크 차단, 저장 부족 및 강제 종료
7. 12시간 대기, 제조사 절전, 재부팅 후 명시적 재활성화
8. 네이버 일정의 기기 제공자 노출 여부 또는 다른 연동 방식 결정
