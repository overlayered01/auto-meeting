# 개발 진행 계획

작성일: 2026-09-13 · 상태: Android 녹음 검증 앱 구현 / 에뮬레이터 일부 검증 / 실제 기기 검증 전

## 1. 이번 단계의 목표

Flutter 기반 앱을 구현하기 전에 자동 녹음, 다중 Google 계정 인증, 캘린더 변경 반영이 실제 사용 조건에서 어느 수준까지 가능한지 확인한다. 기술 검증 결과로 지원 범위와 구조를 정한 뒤 제품 화면과 기능을 구현한다.

다음 요구사항은 유지한다.

- 참석자가 없는 개인 일정을 포함한 캘린더 일정 기반 동작
- 여러 Google 계정을 연결하고 계정별 캘린더 선택
- 일정과 연결된 주변 음성 녹음 및 기기 저장
- 가능한 조건에서 일정 시각에 자동 녹음한다는 제품 목표
- Flutter 사용, 필요한 마이크·예약 동작은 네이티브 코드와 연동

알림을 눌러 시작하는 방식은 기술 검증용 기본 경로이자 자동 시작이 불가능한 상태의 대안이다. 이것만 구현한 결과를 원래 요청한 자동 녹음의 완료로 처리하지 않는다.

| 3 | 기획서 v0.3 및 구현 구조 확정 | 지원 모드, 인증 유지 방식, 동기화 방식, 저장 정책 결정 |

## 3. 기술 검증용 작은 앱

검증용 앱은 계정 연결, 일정 목록, 예약 테스트, 녹음·재생, 진단 화면만 갖춘다. 기능별 결과는 OS 버전·실기기·앱 상태와 함께 기록한다. 목 데이터나 시뮬레이터 결과만으로 백그라운드 녹음 성공을 판정하지 않는다.

### A. 마이크와 예약

다음 경우를 각각 다른 테스트로 취급한다.

1. 앱을 화면에 열고 2분 뒤 자동 시작 및 정해진 길이 후 종료
2. 사용자가 즉시 녹음을 시작한 뒤 화면을 잠가 녹음 유지
3. 녹음하지 않은 대기 상태를 켠 뒤 화면을 잠가 예약 시각에 새 녹음 시작
4. 앱이 백그라운드에 있는 동안 시작 알림을 눌러 녹음 시작
5. 사용자 강제 종료, OS의 프로세스 종료, 재부팅 이후 예약·알림 상태 확인
6. 전화 수신, 다른 앱의 마이크 점유, 수동 종료, 저장 실패 처리

통과 조건: 녹음 파일이 실제 재생되고 시작·종료 시각과 누락 구간을 확인할 수 있다. 마이크가 켜진 시점과 파일 저장 시작 시점을 구분하여 기록한다. 2번 성공을 3번의 근거로 사용하지 않는다.

자동 대기가 검증되지 않은 플랫폼에서는 해당 기능을 지원으로 표시하지 않는다. 사용자의 무인 자동 시작 요구가 필수라면 지원 플랫폼·사용 조건·배포 형태를 다시 결정한 후 구현 범위를 확정한다. 서버를 추가하는 것만으로 기기의 마이크 실행 제한이 해결된다고 가정하지 않는다.

근거: [Android Foreground Service 시작 제한](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [Apple 녹음 지속 동작](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/record?changes=_1).

### B. 여러 Google 계정의 인증 유지

1. 테스트 계정 A를 연결하고 해당 계정의 일정을 읽는다.
2. 테스트 계정 B를 추가한 뒤 A와 B의 일정을 다시 읽는다.
3. 앱을 종료·재시작하고 두 계정의 일정을 각각 읽는다.
4. 액세스 토큰 만료 후 두 계정 모두 새 인증 토큰으로 조회되는지 확인한다.
5. A의 권한 해제·연결 해제 이후 B는 계속 작동하는지 확인한다.

통과 조건: 화면에 계정 두 개를 표시하는 것뿐 아니라 계정별 API 조회와 인증 갱신이 실제로 유지된다. 토큰과 이메일 원문은 진단 로그에서 제외한다.

기본 로그인 플러그인만으로 충족되지 않으면 계정별 인증을 유지할 수 있는 네이티브/OAuth 연동 방식을 검토한다. 인증 서버가 필요하다는 결과가 나오면 서버가 다루는 데이터와 운영 비용을 정리한 뒤 구조를 확정한다. 녹음 업로드는 별도 기능으로 취급한다. [google_sign_in 다중 사용자 제한](https://pub.dev/documentation/google_sign_in/latest/google_sign_in/GoogleSignInAccount-class.html)

### C. 캘린더 변경 반영과 예약 갱신

1. Google Calendar 웹에서 10분 뒤 시작하는 개인 일정을 만든다.
2. 앱이 열린 상태와 닫힌 상태에서 각각 감지 시각을 측정한다.
3. 일정을 이동·삭제하고 기존 예약의 취소와 새 예약 등록을 확인한다.
4. 여러 계정에 동일 일정이 있는 경우 알림과 녹음이 중복되지 않는지 확인한다.
5. 날짜가 진행되어 조회 기간에 새로 들어온 변경 없는 일정과 반복 일정을 확인한다.
6. 네트워크·계정별 조회 실패가 있을 때 기존 예약이 잘못 삭제되지 않는지 확인한다.

초기 검증 구현은 캘린더별 미래 기간을 전체 조회하고 로컬 예약과 비교하는 방식으로 단순화한다. 모든 페이지 조회가 성공한 경우에만 그 범위의 결과를 교체한다. 증분 동기화를 채택하는 경우 미래 기간 보충 조회를 별도로 설계하고 `syncToken`에 `timeMin/timeMax`를 함께 보내지 않는다. [Google Events 목록 API](https://developers.google.com/workspace/calendar/api/v3/reference/events/list)

통과 조건: 마지막 동기화, 조회 범위, 예약 적용 범위가 기록되고 변경·삭제가 중복 없이 반영된다. 외부 변경을 즉시 발견하지 못하는 조건과 실제 지연을 공개한다.

앱을 오래 열지 않아도 일정 변경을 빠르게 받아야 하는 요구가 충족되지 않으면 서버의 Calendar 변경 수신과 모바일 푸시를 평가한다. 웹훅·푸시 도입 후에도 기기 전달과 정각 녹음을 절대 보장한다고 표현하지 않는다. [Google Calendar 변경 알림](https://developers.google.com/workspace/calendar/api/guides/push)

| 검토 문제 | 수정할 내용 |

| 다중 계정 인증 유지 방식 미정 | 계정 추가·복원·토큰 갱신·권한 해제의 처리 방식 |

| 로컬 저장과 OS 백업의 의미 혼재 | 앱 자체 업로드 여부, OS 백업·기기 이전 정책, 내보내기·복원 범위 구분 |
| P0/P1 및 완료 조건 불일치 | 공유·일회성 제외의 우선순위 통일, 단계 합계에 맞춰 일정 재산정 |

이 표는 수정 작업 목록이며 아직 제품 정책을 확정한 결과가 아니다.

## 5. 실제 제품의 첫 사용 흐름

`두 계정 연결 → 캘린더 선택 → 개인 일정 감지 → 녹음 예약 → 검증된 조건에서 시작 → 자동 종료 → 저장 → 재생·내보내기`

화면은 기존 `홈 / 예정 일정 / 녹음함 / 설정`을 유지한다. 홈에서는 다음 상태를 서로 구분한다.

- 일정 정보를 가져온 시각
- 알림 예약 완료 여부
- 녹음 시작에 사용자 조작이 필요한지
- 현재 실제 녹음 중인지

계정 필터는 보기 범위만 바꾼다. 계정의 추적·녹음 활성 여부는 별도 설정으로 표시하여 필터 선택 때문에 예약이 바뀌지 않게 한다.

## 6. 준비물과 작업 경계

- 실제 사용할 Android 또는 iPhone 및 기기 연결
- 다중 계정 검증에 쓸 Google 계정 두 개와 테스트 캘린더
- Calendar API가 활성화된 개발용 Google Cloud 프로젝트 및 플랫폼별 OAuth 설정
- iOS 검증 시 Mac/Xcode 환경

개발 도구 상태 확인, 기획 정리, 검증용 코드 준비는 기기·계정 인증 전에 진행할 수 있다. 실제 기기와 계정 인증이 준비되지 않은 항목은 미검증으로 남긴다. 실제 캘린더 접근과 외부 서비스 생성·배포는 그 작업을 진행할 때 범위와 설정을 구체화한다.

일정은 환경과 테스트 계정이 준비된 뒤 기술 검증 3~5개 작업일을 1차 추정치로 둔다. 인증 방식 변경이나 iOS 환경 준비가 필요하면 늘어날 수 있다. 전체 출시 일정은 이 결과로 다시 산정한다.

## 7. 현재 상태

- 제품 기획서 v0.2에 검토 상태 안내 추가, 상세 정책 수정은 기술 검증 결과에 따라 진행
- 개발 진행 계획 작성
- Flutter·Dart 명령 경로 확인
- `flutter doctor -v` 완료: Flutter 3.41.4 / Dart 3.11.1, Android SDK 36.1.0, Android Studio 내장 Java 21 정상, Android 라이선스 확인 완료
- 실제 Android/iOS 휴대폰은 연결되어 있지 않으며, 별도 Android 16(API 36) 에뮬레이터로 일부 실행 검증 수행
- Flutter 검증 앱과 Android 네이티브 녹음·저장·재생 구현, 실제 검증 상태는 [녹음 검증 기록](RECORDING_LAB.md) 참조
- 정적 분석, Flutter 테스트 10개, Kotlin 정책 테스트 6개 통과 및 Android 디버그 APK 빌드 성공
- 에뮬레이터에서 짧은 예약의 저장·재생 시작, 기본 모드 이탈 취소, 화면을 끈 채 2분 대기 후 1분 녹음·저장 확인. 실제 음성 품질 확인은 아님
- Google 연동 및 실제 휴대폰 검증은 아직 없음

기술 검증이 완료되면 이 문서의 제안과 실제 결과를 구분해 갱신한다.

## 8. 2026-09-16 추가 진행

- 사용자에게서 갤럭시 S23 / Android 16의 이전 잠금 녹음 실험 정상 동작 보고를 받음
- 앱 0.2.0: Android 기기 캘린더 읽기·여러 계정의 캘린더 선택·사용자 활성화 자동 대기·일정 시작 녹음 구현
- 음성 감지는 Silero VAD로 기기에서 처리. 말소리 미감지 60초 또는 일정 종료 시 WAV 저장, 같은 일정 재시작 방지
- Google 인증·동기화는 Android에 등록된 계정에 위임하는 경로를 구현. 위 B절의 앱 자체 OAuth 인증 검증을 완료한 것은 아님
- 네이버는 공식 공개 API의 조회 기능과 Android CalDAV 지원이 없어 연동 경로 확인 대기. 직접 연결 기능을 완료로 표시하지 않음
- 구현 정책과 최신 검증은 [캘린더 녹음 안내](CALENDAR_RECORDING.md)를 기준으로 확인. 제품 기획서 전체 확정 또는 출시 완료가 아님
